# Электронные договоры и дополнительные соглашения в 1С:Университет и Госключ

Лабораторная работа №1 по дисциплине **«Разработка и анализ требований к ПО» (РиАТПО)**.

**Вариант:** 03-Электронные-договоры-и-допсоглашения - сервис электронного подписания договоров и дополнительных соглашений между университетом и студентом.

## Назначение репозитория

Репозиторий содержит документ о концепции и границах кейса **«Переход на электронные договоры и дополнительные соглашения между университетом и студентом»**, матрицу трассировки требований (RTM), журнал ревью и исходные материалы от индустриального партнёра.

**Индустриальный партнёр:** Учебное управление университета (договорной отдел).

**Цель работы:** формализовать ожидания заказчика, определить рамки решения и создать единый источник истины для команды разработки.

**Ключевая идея решения:** расширение «1С:Университет ПРОФ» формирует договор в PDF/A, подписывает его УКЭП вуза и через REST API ЕПГУ отправляет в приложение «Госключ»; студент подписывает документ удалённо, после чего подпись автоматически возвращается в карточку договора.

## Правила формирования коммитов

**Один коммит - одно логическое изменение.** Не «накопил за вечер и отправил всё сразу».

**Формат сообщений:**

    <тип>: <описание с маленькой буквы, без точки>

**Типы:**

| Тип | Когда использовать |
|-----|--------------------|
| `docs` | Документация |
| `feat` | Новая функциональность / раздел |
| `fix` | Исправление ошибки |
| `chore` | Рутина: настройка, конфиги |
| `refactor` | Переработка без смены смысла |

**Примеры допустимых:**

    docs: добавлено введение и бизнес-контекст
    docs: добавлены бизнес-цели BO-1..BO-4
    feat: добавлены сценарии использования UC-1..UC-10
    fix: исправлено отчество в шапке
    chore: добавлены шаблоны в вариант 03

**Недопустимые:**

    update
    fix
    правки
    asdf

## Как устроены ветки и ревью

Работа ведётся через **feature-ветки** с обязательным ревью.

**Схема:**

    main
    ├── feature/group1-header-common-framework     <- Сапунков (общая рамка + разделы 1, 2)
    ├── feature/group2-stakeholders-usecases-nfr   <- Блошкин (разделы 3, 4, 5)
    ├── feature/group3-scope-risks-acceptance      <- Сапунков (разделы 6, 7, 8, 9)
    └── feature/rtm                                <- Блошкин (матрица трассировки требований)

**Процесс:**

1. Автор создаёт feature-ветку от `main`.
2. Работает, коммитит, пушит.
3. Когда всё готово, создаёт **Pull Request**.
4. Ревьюер (другой участник команды) читает diff, оставляет комментарии, заполняет `review_log.md`.
5. Если Approve, автор мерджит PR в `main`.
6. Если Request changes, автор правит, пушит в ту же ветку, PR обновляется.
7. После merge ветка удаляется или сохраняется для истории.

**Ревью по кругу:**

| Кто ревьюит | Кого ревьюит |
|-------------|--------------|
| Сапунков А.Р. | Блошкин Ю.В. (ветки group2, rtm) |
| Блошкин Ю.В. | Сапунков А.Р. (ветки group1, group3) |

## Как запустить работу

**1. Клонировать репозиторий:**

    git clone https://github.com/Susich/ECP_lab1_v2.git
    cd ECP_lab1_v2

**2. Переключиться на свою ветку, ту которую делаешь:**

    git checkout feature/group1-header-common-framework

**3. Работать, коммитить, пушить:**

    git add .
    git commit -m "docs: ..."
    git push

**4. Создать PR на GitHub:**

- **Compare & pull request** → base: `main`, compare: твоя ветка.
- **Reviewers:** кто тебя ревьюит.
- **Create Pull Request**.
